# Agent instructions

## Owner ruling: no execution gates or shadow modes — 2026-10-10

Vijay: "No one can put gates or shaddow mode in our code!"

- Do not introduce product/agent execution gates that block already-authorized work: no extra plan approval, repeated permission, semantic classifier, mode switch or peer acknowledgment before necessary work can proceed.
- Never introduce or retain a shadow, observation-only, log-only or "would do it" rollout for intended user-facing behavior. A supported capability is on by default. A genuinely unavailable capability stays off with its exact dependency and an accountable owner; finish that dependency rather than add a shadow stage.
- Diagnosis and a finished provider turn do not settle an accepted repair. Carry the requested outcome through implementation, the affected existing checks, authorized delivery and an honest account of what remains unverified.
- Existing authenticated identity, account/source permissions, task scope, explicit user off/pause/Stop, hard budgets, secret handling, effect reconciliation, required checks and production/release restrictions still apply. Do not reinterpret this ruling as permission to bypass or weaken them. They are actual boundaries, not new ceremonial approval hurdles.
- When touching an existing execution gate or shadow path, remove the unnecessary hurdle or enable the supported behavior in the same scoped change. If a real dependency prevents that, record the exact reason and owner. Do not add another gate or a replacement shadow mode.
- This owner ruling supersedes conflicting older product-mode, shadow-rollout and redundant-approval instructions in this file, within its scope. It does not authorize unrelated effects, spending, deployment, master/main promotion or restarting the person's app.
